# ADR 0001: Backend Adapter Interface

**Status:** Proposed
**Phase:** 0 (per `CLAUDE.md` build order) — this is the contract everything else depends on; not to be parallelized or handed to a subagent once accepted.

## Context

The SDK's core value prop is letting a game author write multiplayer room logic once and run it on any supported realtime backend (PartyKit for MVP; Colyseus and Supabase Realtime are post-MVP, see `CLAUDE.md`). That only works if there's a single interface backend-specific "adapter" packages implement, and a single interface game code is written against — independent of which adapter is chosen.

Target ICP (`multiplayer-agent-sdk-build-plan.md`) is 2-6 player turn-based/casual games (card games, trivia, tic-tac-toe, party games) built by vibe coders via an AI agent. Explicitly **not** the ICP: latency-sensitive competitive/action games. That constraint shapes the interface below — it optimizes for a simple, agent-generatable pattern over raw throughput or sub-frame sync.

Per `orchestration-plan.md`, the interface must cover: room create/join, state sync, presence, teardown.

## Decision

Use a **server-authoritative action/reducer model** (Redux-shaped), split into two halves:

1. **`RoomDefinition`** — backend-agnostic game logic, written once by the game author (or generated by the agent) against the core SDK. Never imports an adapter.
2. **`MultiplayerAdapter`** — implemented once per backend (PartyKit for MVP). Takes a `RoomDefinition` and produces (a) a deployable server for that backend, and (b) a client connection API.

```typescript
// packages/core — types every adapter and game must agree on

export interface PlayerInfo<TMeta = unknown> {
  id: string;
  meta?: TMeta;
  connectedAt: number;
}

export interface RoomOptions {
  maxPlayers?: number;
  idleTimeoutMs?: number; // adapter tears the room down after this much inactivity
}

export interface RoomDefinition<TState, TAction, TMeta = unknown> {
  createState(): TState;
  onJoin(state: TState, player: PlayerInfo<TMeta>): TState;   // throw to reject the join
  onLeave(state: TState, player: PlayerInfo<TMeta>): TState;
  onAction(state: TState, action: TAction, player: PlayerInfo<TMeta>): TState; // throw to reject the action
  options?: RoomOptions;
}

export interface MultiplayerAdapter {
  createServer<TState, TAction, TMeta>(
    def: RoomDefinition<TState, TAction, TMeta>
  ): unknown; // backend-specific server export, e.g. a PartyKit `Server` class

  connectClient<TState, TAction, TMeta>(
    config: ClientConnectConfig
  ): RoomConnection<TState, TAction, TMeta>;
}

export interface ClientConnectConfig {
  roomId: string;
  host?: string;               // backend-specific connection info (e.g. PartyKit host)
  player: { id: string; meta?: unknown };
}

export type Unsubscribe = () => void;

export interface RoomConnection<TState, TAction, TMeta> {
  readonly state: TState;
  readonly presence: PlayerInfo<TMeta>[];
  send(action: TAction): void;
  onStateChange(cb: (state: TState) => void): Unsubscribe;
  onPresenceChange(cb: (players: PlayerInfo<TMeta>[]) => void): Unsubscribe;
  disconnect(): void;
}
```

**Room create/join** — `onJoin`/`onLeave` hooks on `RoomDefinition`; room creation itself (assigning a room ID, provisioning the backend resource) is an adapter concern exposed via `createServer`, since PartyKit/Colyseus/Supabase each provision rooms differently.

**State sync** — one authoritative `TState` object per room, mutated only by replaying `onAction`/`onJoin`/`onLeave` server-side, then pushed to all clients. No direct client-side state patches. `TState` and `TAction` **must be JSON-serializable** (no functions, class instances, `Map`/`Set`) — this is required for the Supabase adapter to work at all (Postgres/broadcast payloads) and keeps the contract identical for the WebSocket-native backends.

**Presence** — `presence: PlayerInfo[]` alongside state, with an `onPresenceChange` subscription. Each adapter wires this to whatever the backend already tracks (PartyKit connections, Colyseus client list, Supabase Presence) rather than the SDK reimplementing presence tracking.

**Teardown** — `onLeave` for graceful disconnects, plus `RoomOptions.idleTimeoutMs` for adapter-driven cleanup of abandoned rooms. All three MVP-relevant backends support tearing down an idle room/channel natively.

## Alternatives considered

- **Direct/CRDT-style shared state** (clients mutate shared state without server validation): rejected — turn-based games need move legality checks (e.g. "not your turn"), and CRDT merge semantics are unnecessary complexity for 2-6 player turn-based games.
- **No shared interface, each adapter exposes its native API**: rejected — this is just three separate SDKs with a shared npm scope, and drops the actual product thesis ("wrap once, swap backend").

## Consequences

- Game authors (or the agent) write exactly one `RoomDefinition` per game; only the chosen adapter package needs backend-specific code.
- The reducer pattern (`onAction` returning next state) is a well-documented, easy-to-generate shape for an LLM coding agent — this is a deliberate bet in favor of agent-authorability over flexibility.
- The JSON-serializability constraint on `TState`/`TAction` is a hard rule for game authors, not just adapters — should be documented and, ideally, enforced with a lint rule or runtime check in Phase 1.
- Locking this interface now means Phase 2 adapters (Colyseus, Supabase — post-MVP) and all three reference games can be built in parallel without touching each other's files, per `orchestration-plan.md`.

## Non-goals (MVP)

- No matchmaking/lobby/discovery layer (explicitly out of scope — no arcade layer per the build plan).
- No reconnection/session-resumption guarantees beyond a basic reconnect; no state diffing/patching optimization (`TState` is sent whole).
- Not designed for high-frequency (sub-second, e.g. real-time action) sync — matches "not the ICP" in the build plan.

## Open questions for Phase 1 (PartyKit adapter implementation)

- Exact shape of `host`/connection resolution for local dev vs. deployed PartyKit rooms.
- Whether `onAction` validation errors should disconnect the sending client, no-op, or surface an error event on `RoomConnection` — leaning toward a non-fatal error event, to be confirmed while building the PartyKit adapter.
